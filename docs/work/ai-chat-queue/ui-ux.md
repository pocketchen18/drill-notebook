# 人工对话排队与插话 UI/UX

> 2026-11-09，已按人工确认的「贴边队列」与「插话」完成实现及针对性验收，等待人工体验确认，尚未提交 Git。实现与验证范围见同目录 `plan.md`。
> 基线：四个会话工具及并行运行已由用户提交，HEAD `1072f3e`。此前行为见 [派发切片归档](../../archive/v0.7.2/ai-session-dispatch/ui-ux.md)。遵循用户暂不改共享状态文档的约束，本切片仍保留施工目录，状态同步后再归档。
> 参考用户提供的 Codex App 排队条、消息菜单，以及 Qoder「插话」入口；按钮说明采用用户指定的简短文案。交互草图源文件：`chat-queue-preview.html`，在对话中预览；含「贴边队列」「展开列表」两种布局，默认推荐前者。

## 1. 当前切片的闭环

用户在 AI 回复时继续输入，默认发送把消息加入当前会话的队尾；当前回复结束后自动逐条发送。待发送内容始终可见，允许查看、编辑、移除和暂停接续。每条普通排队消息单独产生一轮问答，不合并成一个长提示。

若是补充当前任务，用户可明确点击 **「插话」**，提交给当前运行继续处理。它与等待下一轮的排队是两种动作。使用「插话」这个名称；「插队」容易被理解为只调整队列次序，「引导」不如「插话」直观。

- 新建页规则不变：首条有效发送才创建会话；仅输入不建会话。
- 同一会话顺序执行，不同会话独立运行；切换、收起侧栏不停止队列。
- 本轮聚焦输入区及待发送区，不做 v0.8 整体侧栏改版、供应商 / 模型 / effort 选择。
- 不增加全局「启用排队」设置。回复中发送即排队；暂停只针对当前会话这一批待发消息。
- 插话不停止当前回复；首版不做停止后立即插队、拖动排序或「在侧边聊天中打开」。模型接收补充的边界见第 4 节，不能把提交成功等同于已经生效。

## 2. 输入框与发送动作

输入框继续使用已确认文案 **「正在回复，可先输入下一条问题」**。停止键与发送键分开，输入文字后不会失去停止入口。

| 当前状态 | 主按钮 / 发送快捷键 | 辅助动作 |
|---|---|---|
| 空闲、没有待发消息 | 发送，立即开始一轮 | 无停止键 |
| 正在回复，输入为空 | 发送不可用 | 显示「停止生成」 |
| 正在回复，输入有效 | 加入队列，追加至队尾 | 「插话」与独立的「停止生成」 |
| 队列暂停，输入有效 | 加入队列，继续保留为待发 | 队列头显示「继续发送」 |
| 入队结果确认中 | 「正在加入…」，禁止重复提交同一次输入 | 当前回复仍可停止 |
| 提交结果未知 | 暂停新提交，提示「上次提交结果待确认」并提供「核对提交」；允许继续编辑草稿 | 使用原请求身份核对，不把新草稿重复发送 |

- 回复中默认 Enter 加入队列、Ctrl+Enter 插话，Shift+Enter 换行；空闲时 Enter 正常发送。已有发送键设置优先，若占用了 Ctrl+Enter，则保留原操作，插话使用按钮，不静默改键。中文组合输入确认不提交；快捷键绝不代替停止。草图按默认键位演示。
- 主按钮使用原发送箭头；忙碌时无障碍名称和辅助文案为「加入队列」。有文字时可显示文字按钮「加入队列」，空输入仅显示停止按钮。
- 回复中有有效输入时，主按钮旁提供次要操作「插话」，悬停说明固定为 **「提交，但不中断模型运行」**。不在 tooltip 堆叠执行边界、Agent、API 等术语。停止可使用带无障碍名称的方形图标，窄屏动作区可换行，不能挤掉插话与排队的文字。
- 服务端确认受理后才清空本次已提交的文字和附件，并显示队列项；如果确认期间用户已输入新内容，不清掉新草稿。
- 失败则保留原输入和附件，显示可重试原因。结果未知时先核对同一次提交，不能点击一次重试就产生两条。
- 人工消息沿用现有文本和附件限制，不套用会话工具的短文本限制；不以本轮 UI 设计改变全局运行预算。

## 3. 位置与外观

推荐「贴边队列」：位于输入框上缘，与输入框组成一组，但待发送区和可编辑输入区有清晰边界。不放进已发送聊天气泡，也不做全屏队列管理页。

```text
│ AI 正在继续解释矩阵对角化……                        │
│                                                    │
│ 本地存储 …                                        │
│ ┌ 待发送 2 · 本轮结束后依次发送      暂停接续 ┐     │
│ │ 1  再给一个不能对角化的例子。   ↳ 插话 ⋯ │     │
│ │              展开其余 1 条                │     │
│ └──────────────────────────────────────────┘     │
│ ┌────────────────────────────────────────────┐   │
│ │ 正在回复，可先输入下一条问题                │   │
│ │ ＋             ■ 停止   ↳ 插话 [加入队列 ↑] │   │
│ └────────────────────────────────────────────┘   │
```

- 空队列不占空间。1 条直接显示；多条默认显示第一条及「展开其余 N 条」，展开后按实际顺序展示，允许收起。
- 队列头显示「待发送 N」及「本轮结束后依次发送」；暂停显示「已暂停 · N 条待发送」。等待项使用静态队列图标，不冒充正在调用模型。
- 单行摘要截断，点击正文展开全文、附件名称及本条上下文来源。正文与输入框之间留足间距，避免截图中两层覆盖造成的粘连感。
- `…` 菜单包含 **「编辑消息」「移除消息」** 两项。移除只针对未开始的消息，无删除历史的含义；不使用只有一个删除项的省略号菜单。
- 正在回复时，每条人工队列项右侧直接显示「插话」，说明仍为「提交，但不中断模型运行」。可把任意一条待发消息转为本轮补充，其他条目的顺序不变。编辑期间禁用队列项插话，避免发送未保存的旧内容；空闲时不显示该动作。
- 暂停接续位于队列头，是这一批消息的动作；不塞进每条消息菜单。
- 一屏默认最多展开 3 条；更多可收起或在有界队列区滚动，不能将回复窗口挤没。正式产品窄高视口优先收起队列，不缩小输入区点击目标。
- 备选「展开列表」直接显示多条带序号的两行摘要，独立于输入框；适合经常连续写多条的用户。两种方案行为相同，确认后只实现一种，不增加布局设置。

## 4. 消息生命周期

### 插话

```text
输入草稿 / 一条待发消息 → 正在提交 → 插话 · 等待接收 → 插话 · 已接收
                                             ↓ 当前轮停止 / 失败
                                     保留为暂停的待发消息
```

- 两个入口行为相同：输入区直接插话；或将某条普通待发消息转为插话。只有后端确认仍归属于当前运行后才清空原草稿或移出队列，不能既插话又再执行一次普通排队任务。原有新草稿、附件及其他排队条目不受影响。
- 提交受理后，输入框上方显示补充文字与 **「等待模型接收」**；此时仍属于待接收内容，不放入已发送历史。实际带入模型请求且收到上游接收证据后，移入回复中的独立用户补充，标为 **「插话 · 已接收」**，只保留一次。这里的“已接收”不承诺模型一定遵从；网络结果未知时显示「接收未知」，保留内容并允许移除，不自动重发。整个会话导出也按实际顺序保留已接收插话。
- 当前正在流式输出的请求继续；不关闭连接、不取消正在执行的工具，也不回滚已完成的工作。待当前响应及其工具结果整理完，在下一次模型请求时带入补充。现有 `AiService` 是多次请求组成的工具循环；这里的“本轮”指完整运行，而非单次上游请求。此边界供实现使用，不写进按钮说明。
- 若当前响应没有后续工具调用，但结束确认前已受理插话，则保留原回复，并在同一次逻辑运行中接续处理补充；没有可用预算时明确暂停保留，不能无限重置预算。多条插话按实际受理顺序交给模型，保留独立消息，不等待普通队列，也不打断正在执行的步骤。
- 若提交时原运行已经结束，或已经切入另一条任务，拒绝将补充悄悄发给新任务：原内容留在输入框 / 原队列位置，提示「本轮已结束，请发送或加入队列」。提交请求必须绑定点击时的会话及运行，最终结果以后端确认为准。
- 等待接收期间仍可继续输入或排队；这条插话不再提供编辑、撤回或重复插话按钮。当前轮停止 / 失败时，确定尚未交给模型的人工插话恢复为暂停的待发消息：原队列项尽量回到尚未开始的原相对位置，直接输入的插话按受理顺序保留。已接收的补充留在历史，不重复入队；接收未知则先核对状态。
- 「暂停接续」只暂停后续普通任务，已明确提交的插话仍交给当前运行。待接收插话不计入「待发送 N」；可在会话状态中补充「插话待接收」，避免看起来没有任何等待内容。刷新恢复真实状态；完整重启后，未接收内容按第 6 节暂停恢复，绝不注入另一轮。
- 当前回复与插话的展示按实际事件顺序追加，已生成段落不抹除、不跳回顶部；插话提交不强制滚动到底部。

### 正常接续

```text
输入草稿 → 正在加入 → 待发送 → 已开始（移入聊天记录）→ 完成
                     ↕
                  队列暂停
```

- 队列项得到真实开始确认后，才从待发送区移入正常用户消息，并出现对应助手占位；不闪烁成两份正文。
- 当前轮正常结束后，下一条按受理顺序开始；没有额外倒计时。用户想检查内容，可提前暂停接续。
- 执行历史使用开始时的最新会话记录。人工点击加入时捕获文字、附件、页面上下文及检索范围，避免排队期间切笔记页使提问对象改变；展开详情可核对本条来源。模型沿用受理时配置，不在此另加模型选择。
- 会话列表沿用「待发送 N」。有运行项显示圆环；仅有暂停项显示静态暂停标识和「已暂停 · 待发送 N」，不计入“正在运行”。

### 编辑

1. 点击「编辑消息」，先确认该消息仍未开始，并暂停本会话的自动接续。当前回复继续。
2. 在该队列项内展开文本编辑区和附件清单，显示「保存修改」「取消」。下方新草稿保持原样；普通 Enter 在编辑区只换行，不新发一条。
3. 保存更新原位置，不插到队尾、不新增一条；取消保留原内容。二者都会恢复编辑前的接续状态。若原本已经手动暂停，仍保持暂停。
4. 编辑期间如果当前回复结束，保持队列暂停，直到保存或取消。切会话后编辑草稿保留，并在目标列表标为暂停；不自动提交未保存内容。
5. 如果点编辑时它已开始，提示「这条消息已开始，无法修改」，定位到真实聊天记录，不提供能够误改已发正文的编辑框。

### 移除

- 仅移除尚未开始的条目；保留其它消息顺序，下方新草稿不变。
- 成功后提供短暂「已移除 · 撤销」。撤销后放回仍未开始的原相对位置；如果前面的消息已开始，放在其后，不打断当前轮。
- 点击与开始发生竞争时，以后端结果为准；已开始则移除失败，明确提示，可通过独立停止按钮中止该轮。

## 5. 暂停、停止与失败

| 动作 / 事件 | 当前回复 | 人工待发送消息 |
|---|---|---|
| 暂停接续 | 继续生成 | 保留顺序，后续不自动开始 |
| 继续发送 | 正在生成则等待其结束；空闲则开始下一条 | 依次接续 |
| 停止生成 | 显示停止中，收到确认后结束；已生成内容保留 | 保留为暂停，需人工继续 |
| 上游失败、超时、运行预算耗尽 | 保留真实错误和已生成内容 | 暂停，不连续提交后面的消息 |
| 删除全部待发项 | 不影响当前回复 | 队列区消失，结束这一批暂停状态 |

**相对已提交版本的明确调整**：人工待发文字不能因停止或失败被直接丢掉。列表中的动作统一为「停止回复」，停止后队列显示「已暂停」并保留人工待发内容。会话工具的既有未执行项仍按原规则在停止 / 失败时取消，不为它们引入自动重放。

- 普通人工与工具排队消息共用同一会话的受理顺序；只有用户明确选择「插话」时，才把那一条人工内容改为当前任务的补充。混合队列中工具项展示正文摘要及「来自其他会话」来源小字，计入总数；本切片不开放其逐条编辑或转为插话。新建会话仍是普通会话，不增加创建者分组或接管标识。
- 暂停接续暂时阻止同会话后续任务开始，以免绕过暂停的人工项。恢复时按原受理顺序执行；停止仍按上表分别处理人工项和工具项。
- 「暂停接续」不是取消当前回复，「停止生成」也不是删掉输入。界面不使用含义不清的「关闭排队」。
- 非当前会话的暂停与停止不切走当前页面、不影响别的会话。

## 6. 离开、重启与异常

- 切会话、关闭抽屉、前端刷新：已受理队列由后端持有，刷新恢复同一队列及实际状态；不靠浏览器定时器维持执行，不重复发送。
- **人工已受理的待发内容需要可恢复**：包括确定未接收的插话，完整退出再启动后恢复为暂停，用户明确继续后才发送。作为待发草稿保留，不计入已发送消息数、不参与跨会话读取历史。不能照搬现有工具队列“进程结束后只保留收据”的行为，否则会丢掉人工输入。
- 恢复的人工队列使用加密内容和附件快照，所有落盘在 APP_ROOT；不把明文草稿或凭证写入浏览器存储。保存结构和接口见同目录 `spec.md`。
- 已受理附件缺失、连接配置失效或存储额度不足，标记具体条目「暂时无法发送」，保留人工内容并暂停；提供编辑和重试，不能静默跳过。
- 队列已满时保留输入，提示「待发送消息已达上限，请等待或移除部分消息」；具体上限沿用／复核调度容量，不在 UI 另写死一套。
- 有待发内容（包括暂停）时，删除会话和清理历史提示先处理队列；不会把未发送文字误当历史清理掉。

## 7. 键盘、窄屏与验收

- 320–360px 下摘要可截断，菜单向内展开，不超出侧栏；队列头的说明可换行。文字动作优先保留，触控命中区域至少 44px。
- 不依赖悬停才能发现更多菜单；按钮都有明确名称。Esc 先关闭菜单或正文预览，编辑区 Esc 取消编辑；返回焦点到原入口。
- 入队、暂停、开始和移除使用礼貌播报，不逐 token 打断读屏。增加队列项不抢回复滚动位置；手动上滑仍停止粘底。

| 场景 | 需确认的表现 |
|---|---|
| 回复中连发三条 | 顺序可见，逐条开始，不打断当前回复、不合并消息 |
| 队列项点击插话 | 从普通队列移出，出现等待接收，当前回复持续；不会重复作为下一轮发送 |
| 输入框点击插话 / Ctrl+Enter | 使用当前草稿，不把其他待发项一起送入本轮；组合输入不误提交 |
| 插话进入模型上下文 | 有接收证据才显示已接收；原回复和工具结果仍在；无工具的最终回复也处理已受理补充 |
| 插话与结束同时发生 | 绑定原运行；受理则接续，未受理则保留原内容并提示，不落入其他运行 |
| 插话尚未接收便停止 / 失败 / 重启 | 未接收内容暂停保留；已接收不重复发送；结果未知不假报未发送 |
| 编辑第二条时当前回复结束 | 不提前发出旧内容；编辑仍在，原输入框草稿未变 |
| 入队确认时继续打字 | 已提交部分入队，新草稿留在输入框 |
| 移除 / 开始同时发生 | 只出现一个真实结果，没有假成功或重复消息 |
| 暂停与停止 | 暂停不停止当前轮；停止后人工内容可继续，工具项取消状态明确 |
| 多会话切换与刷新 | 队列、草稿、编辑状态不串会话；刷新不重复发送 |
| 完整应用重启 | 人工待发内容可恢复且暂停，无静默自动发送 |

## 1. 第①组：中文词法召回与 warm 延迟（§9.1、§13.3）

| 零重合不注入 | §9.1.4/§9.1.6 | 通过 |

唯一未命中：查询"这周要刷完什么" vs gold"本周把二叉树遍历刷完"（label 有"刷题"）。原因是**词法召回的同义上限**：这周≠本周、刷完≠刷题，二元组不重合。**不因此放宽安全门槛，也不偷偷加向量服务**（方案 §14 P0a 明确禁止）。P5 可调的只有分词与有限词表（predicateLabel）。

实验过程中修正的两件事，都要写进 P5 的设计约束：

1. 打分必须是 posting 驱动（遍历命中文档），不是"全库 × 查询词"扫描。同一数据下事实-major 扫描中位 0.269ms、posting 驱动 0.017ms。
2. 常见二元组（"笔记""复习"）的 posting 近乎全库，必须设 df 上限（原型取 40%）并对候选做有限截断（原型取 200 条后再套分层排序）。
3. **相关性下限是新发现的必要项**：只按 BM25 排序时，"量子色动力学…"的查询会因为共享一个"力学"二元组被塞进 3 条结构力学目标。原型加了 `matched ≥ 2 且 ≥ 20% 查询词，或 predicate 标签/精确短语命中` 的门，才符合 §9.1.6"不为凑 3 条注入无关记忆"。P5 必须实现同一条规则。
4. 早期一次"p95 995ms 严重超标"的判断是**我自己的单位错误**（纳秒除 1000 当成毫秒）。更正后如上；这条记录保留，防止后续把同一个错误当结论。

## 2. 第②组：fake Clock 下的日预算与摘要门槛（§8.1、§8.4、§8.5、F17/F18/H17/H20）

100 轮同日、每轮 400 估算 Token、两种事件时间表；提取按 4 轮阈值，摘要须同时跨压力/新增量/冷却并按收益 256 判定；满额维护 = 3,000 + 1,024 = 4,024。

| 场景 | 维护调用 | 维护扣账 | 提取 | 摘要 | 排队(PAUSED_BUDGET) | 摘要最大落后 | 未提取轮数 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 快聊：间隔 6 秒 | 9（≤20） | 26,031（≤30,000） | 7 次 | 2 次 | 125 | **77 轮** | **72 轮** |
| 闲置：间隔 61 秒 | 10 | 28,232 | — | 6 次 | 165 | 87 轮 | — |
| 聊天服务 | 100 轮全部正常服务，未被暂停 | | | | | | |

账本口径的机械结论（Ledger 单测）：

- 每次满额 4,024 → **只允许 7 次**（验收 §7.2 的算术成立）。
- 实际用量小 → 预留被归还，可以跑到 **20 次的次数上限**（不是固定 7 次）。
- 全无 usage（UNKNOWN）→ 按预留全额消费，同样 7 次，`unknownAttempts` 计数正确。
- 停在 SENT 未结算的预留**不返还**：悬挂一轮后同日只完成 6 次满额结算，扣账 24,144。
- CHAT 计量但不占后台 20 次/30,000 额度；200 轮聊天后后台额度仍完整。
- 门槛四道独立可测：压力 1,679/1,680、新增量 1,023/1,024、冷却 119/120 秒、收益 255/256；手动 flush 只越过新增量与冷却，不越过压力与收益（H17/H20 的口径）。

**需要用户知情的产品限制**：默认 20 次 + 30,000 Token 在"一天 100 轮"这种重度使用下，只能处理约 28 轮提取源、摘要最多落后 77 轮。方案已规定此时的正确行为——保留硬上限、有界近期历史降级、UI 显示"较早内容未包含"，**不承诺每 4 轮必有已完成摘要**。提高默认额度或取消该目标必须由用户决定，我没有擅自改动默认值。

## 3. 第③组：响应头之后悬挂的取消可靠性（§7.2.2、F11/F12）

loopback `HttpServer` 三种挂法 + JDK `HttpClient`，测试注入 200ms 总期限与有界 await（不靠真实 30 秒 sleep）。

| 场景 | 结果 |
|---|---|
| 头已发、正文永不结束（普通 JSON） | 读取任务在 205–209ms 退出，由期限关闭响应体触发；单一终态；线程池 2 秒内终止；上游只被服务 1 次（取消不变重发） |
| 头已发、正文一段无换行（SSE） | 同上，退出发生在 deadline 附近，**不是等下一个 delta**；首块数据不导致误判完成（原型第一版只 read 一次就"成功"，改成读到 EOF 才判完成） |
| 连响应头都不发 | 未取得响应体时同样取消，`terminalCommits=1`，无泄漏线程 |
| 1ms 退出窗口 | `readerExited=false` 可被观测到 → 支撑"未退出则 worker 标不健康并暂停，不新建线程绕过并发 1"的判定 |

过程中抓到一个真实竞态：期限可能早于响应头到期，此时 `responseRef` 还是空，关闭动作被跳过。按 contracts §7.2.2 原文补上"刚取得响应体时若已取消立即关闭"的分支后，连续 3 次单跑 + 1 次全量并跑全绿。

**结论：P6 的 worker 集成没有被阻塞**，`AiUpstreamClient` 需要的是"总期限 + 可取消 RequestHandle（响应体引用、取消标志、一次性 terminal 门闩）"，而不是只设 `HttpRequest.timeout`。

## 4. 第④组：SQLite 完成回滚与并发容量预留（§2.7、§7、H05/H06/H07/H08）

10 例全绿，用真实 SQLite（项目 DatabaseInitializer 建库）+ 蓝图 `ai_chat_storage` 表：

- **最重要发现：`DatabaseConfig` 现在没有设置事务模式，默认 DEFERRED。两个连接先读账本再写时，后手在锁升级瞬间直接拿到 `SQLITE_BUSY (database is locked)`，busy_timeout 对这种升级不生效**（第一版并发用例就是这样失败的）。容量账本靠 CAS 判胜负就必须用 `TransactionMode.IMMEDIATE`，让第二个写者排队等锁、醒后 CAS 影响 0 行并干净返回 `HISTORY_STORAGE_FULL`。→ P1 必须让账本事务用上 IMMEDIATE，并把这条列为门禁测试（落实位置见本节第 1 条的 P1a 修订：`ImmediateTransaction`，不改全局）。
- 并发 3 个会话抢"恰够一轮"的额度：恰好 1 个成功，账本只加一轮字节 + 一个 2MiB 预留，无负数、无超卖。
- 开始事务提交前抛错：账本字节、预留、revision 全部复原，无 turn 行、无消息行，同会话之后仍能正常开始。
- finalize 按实际落库字节结算并只释放一次；重复释放返回 false 且不二次扣账；实际回复超出预留时**拒绝结算且轮次保持 RUNNING**，不伪装 COMPLETED。
- commit 已成功但应用层收到异常时，失败收尾路径重读后发现已终态，返回既有结果，不把 COMPLETED 改成 FAILED（§7.2.1 分支）。
- 失败收尾：CAS 成 FAILED、`persistence_status=failed`、`memory_eligible=0`，用户输入保留、预留释放一次；重复收尾不再扣账；该会话之后可继续新轮次。
- 超限库：仍可读可统计（按 UTF-8 字节、含明文中文行，不解密），新请求 409 `HISTORY_STORAGE_FULL`，不允许把额度降到 used+reserved 以下，显式调高后可发送。
- 同会话第二个 RUNNING 被部分唯一索引挡住；同 requestId 重发因主键冲突不会重复预留。
- **P1 必须落实的口径**：绕过 begin/finalize 的写入不会更新账本 —— 计数与写入必须同事务，否则账本与实测脱节（原型里显式记录了这条断言）。

回复预留上界算术（H06）：正文+reasoning 合计 1,048,576 原文按最坏对半封装 + result_meta 16,384 + 三份 crypto_meta，最坏 < 1,433,000 < 2,097,152 预留；"把 1MiB 原文当 1MiB 密文"会低估。捕获上限按码点累加，emoji/中文在余量不足时整体停止，不切坏 UTF-8。

## 5. 第⑤组：600 条历史的保留、有界扫描与投影一致性（H01/H02/H03/H11）

5 例全绿：

- 300 轮 = 600 条消息，按 message id 游标、每页 ≤50：12 页取满 + 1 次空页探测，覆盖 600 条、无重复无漏条；翻页全程不删数据，密文快照逐字节不变（H01）。
- 模型侧扫描：一批 ≤16 轮、单请求最多 32 轮 → 实测读 68 行、解密 32 轮、2 条 SQL；更早的 268 轮完全不碰（H03，对照现在 `AiService` 全量 `messages` 拼接的行为）。
- 半轮保护：只纳入消息完整的轮次，游标停在"最旧的一个已纳入轮次"，被 LIMIT 多读到的完整轮次下一批重新读到，不漏轮。
- 摘要替代只按**实际 coverage**：269–284 中留一个缺口 270，270 仍作为原文进入投影，不按 `through` 整段排除；每一轮都有明确去向（纳入/被摘要替代/被裁剪），不静默丢失（T02、H02）。
- 预算裁剪从最旧开始，且最近两轮无论如何保留（§9.2）；投影/请求/检查器共用同一个不可变 plan 对象，来源 ID 与顺序一致（H11 的机制形状）。

## 7. 交给 P1 的硬约束（不得在下一包被破坏）

1. `DatabaseConfig` 必须使用 `TransactionMode.IMMEDIATE`（或等价串行化），否则容量账本的 CAS 在并发下直接抛 `SQLITE_BUSY`。
   > **P1a 修订（口径以 progress §5 P1a 修正记录为准）**：不改全局事务模式——基线
   > `KnowledgePointSummaryService.summarizePoint/summarizeBank` 在 `@Transactional` 内调用 LLM，
   > 全局 IMMEDIATE 会让只读事务也排队等锁、5 秒后 `SQLITE_BUSY`，把知识库总结期间的普通读请求打挂。
   > 落实方式改为原文允许的"等价串行化"：账本事务走 `ImmediateTransaction`（显式 `BEGIN IMMEDIATE`）。
   > "DEFERRED 先读后写必现锁冲突"这条证据已在 P1a 修正里入库为对照用例
   > `ImmediateTransactionTest.deferredReadThenWriteDiesWithBusyInsteadOfRefusing`，防止日后被顺手改回去。
2. 容量账本的字节计数必须与消息写入在同一事务内完成。
3. `reserved_history_bytes` 的释放必须"恰一次"：CAS 标志 + `reserved >= ?` 双条件，禁止用 `MAX(0, …)` 掩盖重复释放。
4. 模型侧历史读取必须走"按轮次倒序、一批 ≤16、单请求 ≤32"的分页方法，禁止复用现有全量 `sessions.messages()` 再裁剪。
5. 摘要替代只按实际 coverage，缺口轮次必须仍作为原文进入投影。
6. 检索必须实现 posting 驱动打分 + df 上限 + 候选截断 + 相关性下限；超时降级为"本轮不使用记忆"，不得半投。
7. 上游调用必须有覆盖建连/头/体的总期限与可取消 RequestHandle；期限早于响应头到达时也要能取消。
8. 默认额度（20 次/30,000、256MiB/256MiB、1MiB/16KiB）不因原型数字难看而调整；要改由用户决定。
